# 寺庙香客服务 · 自适应并发限流器

为「网上预约、点灯祈福、斋饭订餐」这类香客系统设计的 Go 自适应并发限流组件。
初一十五、节庆时请求量可涨十几倍，下游数据库一旦变慢会拖垮所有接口。
本组件按**观测到的往返延迟自动调节并发上限**，装在服务入口和调下游的客户端两处，
在保护下游的同时尽量多放行请求，并对高优先级请求（法会预约、支付）做刚性保护。

## 目录结构

```
internal/limiter/   自适应限流器核心组件（可独立复用，无外部依赖）
  types.go          优先级、结果类型、配置与状态快照
  rtt.go            定长环形缓冲：RTT 样本、最小基线、p50/p90/p99 分位
  algorithms.go     两种自适应算法：Vegas 基线比、Gradient 梯度（可热切换）
  limiter.go        准入控制、强信号减半、探底重测基线、分档预留、平滑
  waitqueue.go      有界优先级等待队列（高档排最前）
internal/sim/       仿真平台
  downstream.go     动态容量下游（容量突降、延迟漂移、周期卡顿、有界排队、过载）
  scenarios.go      34 个固定种子场景（四类故障 + 复合 + 温和过载验收组）
  runner.go         非齐次泊松流量、双层限流串联、超时与强信号贯通
  metrics.go report.go  指标采集、分档计数、收敛分析、报表
internal/demo/      带监控页面的实时演示服务（4 个接口、持续流量、节庆开关）
cmd/bench           34 场景 × 3 模式对比测试主程序（验收入口）
cmd/trace           单场景轨迹诊断工具
cmd/demo            监控页面 HTTP 服务
```

## 八条需求的实现位置

| # | 需求 | 实现 |
|---|------|------|
| 1 | 最小 RTT 基线 + 当前/基线排队比，平滑调上限 | `rtt.go` 取窗口最小 RTT 为基线，`algorithms.go` Vegas 按排队比 Little 定律收缩、满载加性增，`limiter.go applyTarget` 指数平滑 + 单步变化率钳制 |
| 2 | 基线随下游变慢漂移，定期压低并发重测 | `limiter.go` 探底机制：只在满载且无排队时把上限临时压到 70%，用探底窗口最小 RTT 刷新基线；高压/空载均不探，避免误砍 |
| 3 | 梯度算法：延迟随在途上升就收缩，平稳就放大，可切换 | `algorithms.go gradientTarget`，按 RTT 窗口新老两半的延迟梯度与在途变化决策；`SwitchAlgo` 运行时热切换 |
| 4 | 分档优先级，紧张时先拒低档、保留高档额度 | `limiter.go admit` + 动态预留（按高档实时流量占比刚性留槽）+ `waitqueue.go` 优先级等待队列，高档等待超时还放宽 2.5 倍 |
| 5 | 调低上限不取消在途，只停发新请求，等在途降到新上限 | 上限只影响后续 `Acquire`，已发 `Lease` 不被撤销；下游缩容同样不取消在途（`downstream.go` debt 记账） |
| 6 | 过载/超时强信号立即减半，恢复时线性增加 | `Release` 识别 `OutcomeOverload/Timeout` → `recordStrong` 上限减半并进入冷却，冷却期每样本 +1 线性恢复 |
| 7 | 每个接口独立计算，实例间不通信 | 每个 `Limiter` 自带独立 RTT 环、基线、上限、等待队列，无任何全局状态 |
| 8 | 超时取消的请求也计入延迟样本 | `Lease` 在 `Release` 时无条件写入 RTT 环；仿真里超时请求会等下游 `Call` 返回真实经过时间再记录 |

## 运行方式

```bash
# 1) 完整对比验收：34 场景 ×（vegas / gradient / 固定上限）
go run ./cmd/bench -dur 12 -parallel 8

# 2) 单场景轨迹诊断（看上限、在途、等待队列、基线随时间变化）
go run ./cmd/trace -scene 19 -mode vegas -dur 12   # scene 1..34, mode: vegas|gradient|fixed

# 3) 监控页面（默认 :8080）
go run ./cmd/demo -addr :8080
# 浏览器打开 http://localhost:8080/
#   - 顶部切换 Vegas / Gradient 算法（热切换，立即生效）
#   - 一键开关节庆模式：流量涨十几倍，并周期性触发下游容量突降
```

## 仿真与验收方法

- **流量**：非齐次泊松过程，平稳期约为下游容量的 70%，尖峰期乘 10~15 倍；
  全部场景用硬编码随机种子，任何机器结果一致。
- **下游故障**：容量突然下降（含反复震荡）、服务时间线性漂高、周期性卡顿、
  主动过载返回，以及三者复合，共 34 个场景。
- **对照组**：固定并发上限（取初始容量），与两种自适应模式同种子对比。

### 验收口径与结果（`go run ./cmd/bench`）

| 验收项 | 口径 | 结果 |
|--------|------|------|
| 成功率不劣于固定上限 | 34 场景逐一对比 | vegas / gradient 均 **34 胜 0 负** |
| 延迟分位 | p90 改善 ≥25%（主判据）且 p99 改善 ≥7% | p90 改善 ~31%，p99 改善 ~10%，**通过** |
| 上限收敛 | 容量平稳场景稳态饱和窗口 MAPE ≤35% | vegas 18.5% / gradient 19.5%，**通过** |
| 高档 SLO（温和过载） | 物理可达的 3 倍过载，高档成功率 ≥95% | 两算法均 **100%** |
| 高档保护（极端过载） | 十几倍过载下高档率/整体率 ≥2x，且不劣于固定 | 保护倍数 ~10.5x，**通过** |

**关于极端过载下的高档成功率**：十几倍流量时下游物理吞吐只能服务约 1/12 的请求，
任何算法都无法让全部请求成功。因此分两档验收——温和过载（吞吐足够）要求高档 ≥95%；
极端过载用「高档相对整体的保护倍数」衡量，实测高档成功率是整体的约 10 倍。

### 关键设计决策

1. **本地等待与下游延迟分离**：请求在限流等待队列里排队的时间不计入 RTT 控制信号，
   否则限流器会把本地排队误判成下游拥塞而过度收缩。`Lease` 分别记录入队时刻与获额时刻。
2. **等待队列状态机用 granted/canceled 两个互斥标志**，不能用一个布尔位表达两种结局，
   否则被正常唤醒的请求会被误判为超时（开发中实测踩到并修复，见 `waitqueue.go`）。
3. **动态容量信号量用独立 debt 字段记缩容欠账**，维护
   `inflight + tokens - debt == capacity` 不变量，缩容不取消在途、扩容优先唤醒排队者。
4. **探底只在满载且无排队时进行**，避免在故障窗口或空载时无谓砍半上限。
